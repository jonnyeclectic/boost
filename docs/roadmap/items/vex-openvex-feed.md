<code>OSPS-VM-04.02</code> — a Level 3 Baseline criterion <a
href="roadmap.html#osps-baseline-levels">the audit</a> hadn't reached — asks for a VEX
document accounting for vulnerabilities that don't affect the project, with the
non-exploitability reasoning attached. boost already had that reasoning; it just wasn't in a
form a consumer could ingest. CodeQL dismissals carry a <code>#
codeql[rule-id]</code> comment, <code>.gitleaks.toml</code> allowlists boost's own synthetic
secret-scanner fixtures, and <code>.github/zizmor.yml</code> documents six ignores by reason.
<a href="https://openvex.dev/">OpenVEX</a> 0.2.0 turns those into
a published document at <code>docs/vex/openvex.json</code>,
generated by <code>scripts/build_vex.py</code> from one statement file per finding under
<code>docs/vex/statements/</code> — the same one-file-per-item convention the roadmap boards
themselves use, wired into <code>make generate</code> and a <code>--check</code> freshness
gate in CI.
<b>Four statements, and every one traces to a real, already-merged suppression</b> — not an
invented CVE. boost has never had one, so nothing here is named <code>CVE-</code> or
<code>GHSA-</code>; each statement's vulnerability name is the scanner's own rule id instead
(<code>codeql:py/clear-text-logging-sensitive-data</code>, <code>gitleaks:...</code>,
<code>zizmor:dangerous-triggers</code>, <code>zizmor:adhoc-packages</code>).
<b>This satisfies one criterion, not the level.</b> <code>OSPS-QA-07.01</code> — a non-author
human approval before merge — is the wall Level 3 hits regardless, and this change does not
move it; <code>docs/openssf-badge.md</code> tracks the passing-badge criteria only and has no
Baseline rows to flip, so the record lives here and in
<code>docs/security-design.md</code>
instead.
